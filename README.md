# FitLife

Plataforma Django para socios, administración, recepción e instructores. La interfaz se encuentra en `templates/views/html`, `templates/views/css` y `templates/views/js`; el esquema operativo de PostgreSQL está en `database/schema`.

## Organización del backend

Las vistas de la API están separadas por dominio en `api/views/`: autenticación, membresías, personal, dashboard, clases y reservas, trabajo profesional por especialidad, recursos e ingreso por QR. `common.py` concentra utilidades compartidas de autenticación, respuestas JSON y acceso SQL. `api/views/__init__.py` conserva la fachada `api.views` para mantener compatibles las rutas existentes.

## Organización de estilos

Los estilos compartidos, públicos y autenticados se encuentran separados en `templates/views/css/fitlife.css`, `fitlife-public.css` y `fitlife-dashboard.css`, respectivamente. `templates/base.html` carga los tres en ese orden para conservar la cascada y las adaptaciones existentes.

El módulo **Usuarios** incluye un administrador de datos para las tablas operativas del esquema. Los pagos, el historial de accesos y la presencia derivada no son editables desde este módulo; las reservas y sesiones usan las reglas de negocio para reservar, cancelar y promover listas de espera. Las contraseñas se guardan con hash y los tokens QR no se muestran en las consultas.

Las rutas web inexistentes muestran una página propia con acceso directo al inicio y conservan la respuesta HTTP 404. Las rutas `/api/` inexistentes reciben una respuesta JSON 404.

## Puesta en marcha

1. Crea la base de datos PostgreSQL `fit_db`.
2. Ejecuta `database/schema/1.0.sql` a `database/schema/1.21.sql` en orden sobre esa base. El backend espera el esquema `fitlife` creado por el primer script. La versión 1.6 agrega horarios y coordenadas requeridos al crear o editar sedes; la versión 1.7 relaciona planes con sedes, la 1.8 añade la imagen de portada opcional, la 1.9 agrega Webpay como medio de pago, la 1.10 añade el tipo de plan y la región/ciudad de cada sede, la 1.11 asigna instructores a sedes y valida la sede de sus clases, la 1.12 agrega vestidores y duchas con sus cantidades máximas y la 1.13 asocia cada membresía a una sede y limita su uso a esa sede. La migración 1.14 establece `persona.rut` como clave primaria y asocia los registros existentes; la 1.15 renombra a `rut` las columnas de relación de `usuario`, `usuario_rol`, `socio`, `instructor` y `prueba_socio`; la 1.16 impide que un teléfono esté asociado a más de una persona; la 1.17 agrega membresías con acceso global y planes de prueba gratuita asociados a una sede; la 1.18 permite asignar cada máquina a una sala de su sede; la 1.19 añade la asignación de una sede por cuenta de recepción; la 1.20 clasifica puntos de acceso de estacionamiento, disponibles solo cuando la sede tiene estacionamiento habilitado. La migración 1.21 agrega asignaciones administrativas de socios a profesionales, herramientas estructuradas de seguimiento por especialidad y datos de planificación para clases de Monitor. Las cuentas de recepción ya existentes deben recibir una sede desde Administración después de aplicar la migración 1.19. Las máquinas antiguas quedan sin sala asignada hasta que se les asigne una desde la administración. Así, las tablas relacionadas también usan `rut` y no `persona_id`. Como esta base contiene datos de prueba desechables, también puedes recrearla desde cero antes de aplicar todos los scripts. Si la migración 1.16 encuentra teléfonos duplicados ya guardados, resuelve esos duplicados antes de aplicarla. La migración 1.13 asocia automáticamente los registros antiguos cuando su plan pertenece a una sola sede; los casos ambiguos quedan como “Sede no asignada” para revisión.
3. Instala dependencias con `pip install -r requirements.txt`.
4. Copia `.env.example` como `.env` y completa `DB_USER` y `DB_PASSWORD` con las credenciales de tu instalación PostgreSQL. El archivo `.env` se carga automáticamente y no debe compartirse. `DB_NAME`, `DB_HOST` y `DB_PORT` también se pueden ajustar allí. Genera una `DJANGO_SECRET_KEY` privada; por ejemplo, con `python -c "import secrets; print(secrets.token_urlsafe(64))"`.
5. Ejecuta `python manage.py migrate` para crear las tablas internas de Django.
6. Inicia Django con `python manage.py runserver`.

En Windows PowerShell, puedes crear la copia inicial con `Copy-Item .env.example .env`. Después edita `.env` y establece la contraseña de PostgreSQL y una clave privada para Django. No copies secretos a Git, incidencias, capturas ni logs.

Las cuentas nuevas se crean como socios, pero no reciben una credencial QR hasta contar con una membresía vigente. Un administrador puede crear cuentas de recepción e instructores, administrar los roles de las cuentas y asignar perfiles de monitor, entrenador personal, coach o preparador físico. También puede programar clases y configurar planes, beneficios, pruebas gratuitas por sede y membresías globales. La tabla de membresías es de consulta; no permite asignar ni cancelar membresías manualmente. Los socios pueden canjear una prueba gratuita una sola vez, sin medio de pago ni cobros posteriores. Los planes pagados se contratan desde **Planes disponibles** y se pagan con tarjeta de débito o crédito en el checkout alojado de Transbank Webpay Plus; no se acepta efectivo ni se recopilan datos de tarjeta en FitLife. La sede seleccionada queda como sede principal de la membresía; si el plan es global, sus beneficios y acceso aplican a todas las sedes activas. La membresía pagada se activa únicamente después de verificar la aprobación y el monto de la transacción con Transbank. PostgreSQL también impide activar una membresía pagada sin un pago aprobado coincidente. En Recursos se administran máquinas, sedes, salas, cantidad de lockers y cupos de estacionamiento de cada sede. El estacionamiento también se puede ofrecer como beneficio del plan y aparece en la membresía y credencial del socio cuando corresponde.

El panel y la navegación del instructor dependen de su perfil. Monitor puede programar clases en sus sedes y salas asignadas, consultar participantes e historial y registrar asistencia y observaciones. Entrenador personal dispone de evaluación inicial, planes con rutinas y ejercicios, sesiones y progreso. Coach registra objetivos, compromisos, sesiones y adherencia. Preparador físico registra pruebas, resultados y planificaciones por etapas, volumen e intensidad. Administración controla las asignaciones profesional-socio desde **Usuarios → Administrar datos del sistema → Asignaciones profesional-socio**; los instructores no pueden elegir ni asignarse socios. El servidor valida la especialidad, la asignación y el acceso a cada socio y operación, además de restringir la programación de clases grupales a Monitor. La API especializada se encuentra en `/api/professional/workspace`; los registros por especialidad se guardan en tablas propias y no en el seguimiento genérico.

La sección pública **Sedes** muestra tarjetas con imagen, dirección y suscripciones desde la base de datos, con búsqueda por sede o ciudad. La ficha de cada sede incluye áreas, características, horario y clases grupales filtrables por día. El hub autenticado ofrece el mismo directorio en **Tu gimnasio**. Administración ingresa dirección y horarios, pega el enlace compartido de Google Maps para ubicar la sede y asigna suscripciones al crear o editar cada sede; el sistema valida el dominio y obtiene las coordenadas del enlace. La imagen de portada es opcional. Los perfiles profesionales (monitor, entrenador personal, coach y preparador físico) pueden generar una credencial QR de equipo para registrar entradas y salidas sin membresía de socio.

Al programar o editar una clase, administración puede cargar una imagen JPG, PNG o WEBP de hasta 5 MB. Se optimiza y guarda en `media/fitlife/classes`; `1.2.sql` agrega `sesion_clase.imagen_url` para registrar su dirección. En producción, configura el servidor web o almacenamiento de medios para servir el contenido de `MEDIA_ROOT`.

Para crear el administrador inicial de FitLife, define `FITLIFE_ADMIN_RUT` con un RUT válido y ejecuta `python manage.py bootstrap_admin`. El comando detecta las columnas de la base actual y funciona tanto con el esquema anterior (`documento_identidad`/`persona_id`) como con el esquema actualizado (`rut`). En desarrollo genera una contraseña aleatoria y la guarda localmente como `FITLIFE_ADMIN_PASSWORD` en `.env`; el correo predeterminado es `admin@fitlife.cl` y se puede cambiar mediante `FITLIFE_ADMIN_EMAIL`. Consulta la contraseña en tu `.env` para iniciar sesión. El comando no reemplaza ni modifica cuentas existentes. Antes de usar la aplicación con el esquema nuevo, aplica todas las migraciones SQL hasta la 1.19.

## Seguridad, privacidad y calidad

Se incorporó una línea base inicial para configuración segura, política de contraseñas y CI. Esto **no significa que el proyecto esté certificado ni que cumpla integralmente** las normas indicadas. Consulta [el estado de implementación y brechas](docs/compliance/IMPLEMENTATION_STATUS.md) y [la hoja de trabajo del aviso de privacidad](docs/compliance/PRIVACY_NOTICE_WORKSHEET.md). Antes de producción deben cerrarse las decisiones organizacionales y legales allí enumeradas, realizar una revisión independiente y probar el despliegue real. El flujo actual conserva el JWT en `sessionStorage` y no tiene mitigación distribuida de fuerza bruta; son brechas explícitas, no controles ya resueltos.

Para producción, configura `DJANGO_DEBUG=false`, una clave aleatoria de al menos 50 caracteres y `DJANGO_ALLOWED_HOSTS` con los dominios exactos. La aplicación habilita HTTPS redirect y HSTS por defecto en ese modo. Activa HSTS para subdominios o preload únicamente cuando se haya confirmado que todos los dominios afectados sirven HTTPS. Solo configura `DJANGO_TRUST_PROXY_SSL_HEADER=true` si el proxy inverso elimina encabezados reenviados del cliente y establece el suyo; configura `DJANGO_CSRF_TRUSTED_ORIGINS` con orígenes HTTPS exactos cuando sea necesario. Configura SMTP mediante `DJANGO_EMAIL_*` si se habilitan flujos de correo. `check --deploy` forma parte del workflow de calidad; debe ejecutarse también con la configuración del entorno destino.

## Autenticación y pagos

El inicio de sesión acepta correo electrónico o RUT junto con la contraseña, y entrega un JWT firmado HS256 con duración de ocho horas que identifica a la persona por su RUT. Después de aplicar la migración 1.14, las sesiones anteriores deben iniciar sesión nuevamente. Las contraseñas nuevas deben tener al menos 12 caracteres y superar los validadores de Django. La base guarda la contraseña con el hash de Django y la credencial QR como SHA-256; el token QR se genera únicamente para el socio.

Las compras de membresías usan el SDK oficial de Transbank Webpay Plus. Para probar, configura `WEBPAY_ENVIRONMENT=test`; el SDK utiliza el comercio de integración. Para producción, define `WEBPAY_ENVIRONMENT=production`, `WEBPAY_COMMERCE_CODE` y `WEBPAY_API_KEY` con las credenciales privadas entregadas por Transbank. Configura `WEBPAY_RETURN_URL` con una URL HTTPS pública que apunte a `/api/payments/webpay/return` (para pruebas locales se necesita un túnel HTTPS accesible desde Transbank). Ejecuta también `database/schema/1.9.sql` y `database/schema/1.10.sql`. El checkout recibe tarjetas de débito y crédito; el cliente ingresa sus datos directamente en Transbank. Las reservas de clases con precio todavía quedan pendientes de pago.

Para desarrollo visual sin PostgreSQL se puede usar `FITLIFE_DB_ENGINE=sqlite`; las operaciones de negocio requieren PostgreSQL con ambos esquemas SQL aplicados.
